# SlackingOffTimer 移动端技术可行性评估（Prototype）

## 1. 结论摘要

1. Android：可做可验证。可通过前台服务 + 解锁事件 + 本地通知实现 MVP 级“无感计时”。
2. iOS：不能等价实现。无法在后台持续监听“手机解锁事件”并对任意 App 使用进行计时。
3. 建议路线：先 Android 上线验证核心价值，再做 iOS 降级版（主动打开查看 + 定时提醒）。

## 2. 需求逐条可行性

| 需求 | Android | iOS |
|---|---|---|
| 一次配置后后台常驻 | 可行（Foreground Service） | 不可等价（后台执行严格受限） |
| 工作时段内“解锁手机自动计时” | 可行（`ACTION_USER_PRESENT` + 会话逻辑） | 不可行（无公开 API 持续监听解锁） |
| 不影响其他使用 | 可行（后台服务） | 部分可行（只能做有限后台任务） |
| 下班推送今日摸鱼小计 | 可行（Local Notification） | 可行（UNUserNotificationCenter） |

## 3. Android 原型方案

### 3.1 关键技术

- `ForegroundService`：保持计时引擎存活
- `BroadcastReceiver`：
  - `Intent.ACTION_USER_PRESENT`（解锁）
  - `Intent.ACTION_SCREEN_OFF`（熄屏）
- 本地存储（SharedPreferences）：配置、每日统计、今日是否已推送
- 本地通知（Notification Channel）：下班推送“推送：摸鱼小计”

### 3.2 验证点

1. 服务在后台持续运行（前台通知可见）
2. 解锁触发自动开会话（仅工作窗口）
3. 熄屏自动停止会话并结算分钟
4. 下班时间后触发“推送：摸鱼小计”，且每天只推送一次

### 3.3 已知风险

1. 厂商省电策略可能杀死服务（需要引导用户关闭电池优化）
2. 部分机型的解锁广播行为存在差异（需真机矩阵验证）
3. Android 13+ 推送需用户授权 `POST_NOTIFICATIONS`

## 4. iOS 现实边界

1. 无公开 API 支持第三方 App 持续监听“系统解锁事件”
2. 无法在后台长期运行通用计时逻辑（除特定后台模式）
3. Screen Time 相关能力不适用于普通第三方统计任意 App 使用时长的需求

## 5. iOS 建议降级

1. 降级目标：不做“解锁即自动计时”
2. 保留价值：
  - 主动打开后查看当日/趋势
  - 下班时间本地提醒复盘
  - 手动开始/结束专注会话

## 6. 下一步开发建议

1. 先基于 `android-poc` 补一个轻量设置页（可改工作制度）
2. 加入电池优化白名单引导页和保活诊断页
3. 做 3~5 台 Android 真机稳定性压测（12h/24h）
4. 评审 iOS 降级 PRD，再并行开发 iOS 版本
